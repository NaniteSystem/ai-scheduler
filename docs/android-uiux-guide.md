# Android UI/UX, архитектура и UI-kit в Figma

## Введение

Этот документ — практический гид по созданию современных Android-приложений. Он объединяет три направления:

1. **UX/UI-проектирование**: как понять пользователя, спроектировать сценарии и сделать удобный интерфейс.
2. **Визуальный дизайн и Figma**: как построить UI-kit на основе Material Design 3 и подготовить макеты к разработке.
3. **Архитектура и Jetpack Compose**: как устроить код, чтобы приложение было стабильным, производительным и легко поддерживаемым.

Документ ориентирован на начинающих дизайнеров и разработчиков, которые хотят работать в связке «дизайн → код». В основу легли материалы Нетологии, DD Planet, Infogra, AppCraft и официальной документации Google по Material 3, Jetpack Compose и архитектуре Android.

> **Ключевая мысль:** дизайн-процесс — это не только создание красивых картинок, но и продумывание логики, исследование пользователей, тестирование и контроль разработки. Сам дизайн — лишь часть пазла.

## Часть 1. Чем мобильный UX/UI отличается от веба

### Принципиальная разница

Дизайн мобильных приложений похож на создание мобильной версии сайта, но с дополнительными возможностями и более жёсткими ограничениями. Главная задача — создать удобную экосистему с совершенным UX.

Когда пользователь скачивает приложение, он по умолчанию лоялен: уже совершил целевое действие. Если приложение решает его проблему — он будет пользоваться регулярно. Но если хотя бы один раздел неудобен или не работает, человек удалит приложение и, скорее всего, не вернётся. Повторное скачивание — исключение, а не норма [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui).

В вебе пользователь может сравнивать несколько продуктов и вернуться позже. В мобильном приложении у вас есть одна короткая попытка произвести впечатление.

### Специфика мобильного устройства

| Параметр | Веб | Мобильное приложение |
|----------|-----|----------------------|
| Экран | Большой | Маленький, 6 дюймов в среднем |
| Сессии | Длинные | Короткие, частые, прерывающиеся |
| Контекст | Стационарный | «На ходу», одна рука, движение, плохое освещение |
| Ввод | Мышь/клавиатура | Большой палец, жесты, неточный ввод |
| Навигация | Меню, ссылки | Жесты, нижняя навигация, FAB |
| Формы | Могут быть длинными | Лучше дробить на шаги |
| Оффлайн | Реже критично | Часто нужен базовый функционал |
| Отношение пользователя | Можно вернуться | Удаляют быстро и не возвращаются |

Смартфоном пользуются в любой ситуации: на прогулке, в магазине, в автомобиле, занимаясь спортом. На экране должно быть минимум информации — только полезная. Пользователь должен быстро получать доступ к контенту [2](https://netology.ru/blog/09-2020-design-prilojeniy).

### Практические правила мобильного UX

- На каждом экране оставляйте только ключевые элементы.
- Минимизируйте количество шагов до целевого действия.
- Делайте интерактивные элементы достаточно крупными (минимум 48 × 48 dp для Android).
- Длинные формы дробите на шаги или заменяйте на более простые вводы.
- Учитывайте состояния загрузки, ошибки, пустых данных и отсутствия интернета.
- Проектируйте для одной руки: основные действия должны быть в зоне досягаемости большого пальца.

## Часть 2. Компетенции мобильного дизайнера

### Хардскиллы: база, на которой строится интерфейс

По словам Алексея Комарова, UX/UI-дизайнера в IBM и преподавателя Нетологии, дизайнер приложения отвечает за эмоции от использования продукта. Для этого нужно создавать не только привлекательный визуальный облик, но и уметь выяснять потребности пользователей, составлять навигационную модель и проектировать интерфейс с чёткой иерархией [2](https://netology.ru/blog/09-2020-design-prilojeniy).

#### 1. Колористика

Искусство сочетания цветов. Важно понимать, какие цвета гармонируют, а какие «перекрикивают» друг друга. Например, зелёный и красный вместе — насыщенные цвета, которые создают «вырвиглазный» интерфейс и снижают контрастность.

Инструменты для подбора палитр:

- [Material palette](https://www.materialpalette.com/)
- [Adobe Color](https://color.adobe.com/ru/create/color-wheel)
- [Coolors](https://coolors.co/) — создание палитры по фото
- [Color tool (Material Design)](https://material.io/resources/color/) — распределение цветов

#### 2. Типографика

Умение оформлять текст через набор и вёрстку. Дизайн — это оформление контента, 80% которого передаётся через текст. Любая информация располагается в виде иерархии: главная и второстепенная части выделяются через стилизацию.

- Используйте уровни заголовков (H1, H2 и т.д.) для структуры.
- Выравнивайте текст по левому краю — это удобнее для чтения.
- Различайте размер, вес и цвет для создания иерархии.

#### 3. Композиция

Умение грамотно управлять объектами в пространстве: размеры, отступы, расстояния, связи между элементами. Хорошая композиция помогает создать гармоничный и понятный интерфейс.

### Инструменты дизайнера

#### Графические редакторы

| Инструмент | Особенности |
|------------|-------------|
| **Figma** | Кросс-платформенный онлайн-редактор. Работа всей командой, включая заказчиков. Бесплатный для одного пользователя. Сейчас основной инструмент для UI/UX. |
| **Sketch** | Платный редактор для macOS. Дольше на рынке, больше интеграций. Не кросс-платформенный, сложнее работать с заказчиками. |
| **Adobe XD** | Приложение Adobe для прототипирования. Есть возможность создавать голосовые прототипы. Менее популярен, чем Figma. |

Графические редакторы достаточно похожи: освоив один, изучить другой несложно [2](https://netology.ru/blog/09-2020-design-prilojeniy).

#### Дополнительные инструменты

- **Miro** — брейнштормы, mindmap, Customer Journey Map, обсуждение гипотез.
- **InVision, Marvel, ProtoPie, Flinto, Principle for Mac** — прототипирование и микроанимации.
- **Zeplin** — передача макетов разработчикам с отступами и размерами.

### Soft skills

#### Коммуникационные навыки

Больше половины рабочего времени дизайнер общается, согласовывает и обсуждает. Важно уметь доносить свои решения до заказчика, разработчиков и других членов команды. При этом непрерывное общение может привести к выгоранию, поэтому важно периодически прислушиваться к себе [2](https://netology.ru/blog/09-2020-design-prilojeniy).

#### Реакция на критику

Дизайнеров постоянно критикуют. Важно понимать: критикуют работу, а не личность. Главное — получать конструктивную критику. Если сказали «плохо», но не объяснили почему — это неаргументированное мнение, на которое не стоит реагировать. Относитесь к процессу с юмором.

## Часть 3. Базовые принципы UX/UI для мобильных приложений

### Что такое UX и UI

- **UX (User Experience)** — общий пользовательский опыт: путь пользователя по экранам, сценарии использования, удобство и скорость достижения целей.
- **UI (User Interface)** — визуальное представление этого опыта: цвет, типографика, иконки, иллюстрации, анимация и звуки.

Хороший мобильный дизайн минимизирует три вида нагрузки [2](https://netology.ru/blog/09-2020-design-prilojeniy):

| Вид нагрузки | Проявление | Как решать |
|--------------|------------|------------|
| Когнитивная | Усилия для распознавания объекта и принятия решения | Упрощать сценарии, убирать лишнее |
| Визуальная | Слишком много элементов на экране | Делать иерархию, давать воздух |
| Моторная | Жесты, тапы, свайпы | Крупные зоны нажатия, удобные жесты |
| Внешняя | Отвлечения: собака, дождь, машина | Проектировать под контекст использования |

### Классические визуальные принципы

| Принцип | Суть | Пример применения |
|---------|------|-------------------|
| **Масштаб** | Важные элементы крупнее, 2–3 уровня размеров | Заголовок 22 px, текст 16 px, подсказка 12 px |
| **Иерархия** | Взгляд ведёт по важности | Сначала заголовок, потом кнопка действия |
| **Баланс** | Визуальный вес распределён равномерно | Симметрия для спокойствия, асимметрия для динамики |
| **Контраст** | Различия по цвету и размеру показывают разницу функций | «Сохранить» — акцент, «Отмена» — вторичная |
| **Гештальт** | Пользователь группирует близкие/похожие элементы | Карточки с отступами воспринимаются как целое |

### Гештальт-принципы в интерфейсе

По материалам DD Planet [3](https://www.ddplanet.ru/baza-znaniy/uiux-mobile/):

- **Сходство** — похожие элементы воспринимаются как группа.
- **Продолжение** — глаз следует по линии или направлению.
- **Замкнутость** — мозг дорисовывает неполные формы до целых.
- **Близость** — близкие объекты воспринимаются как связанные.
- **Общая область** — элементы внутри одной области группируются.
- **Фигура/фон** — пользователь отделяет объект от фона.
- **Симметрия** — симметричные элементы воспринимаются как единое целое.
- **Общая судьба** — элементы, движущиеся или изменяющиеся вместе, воспринимаются как связанные.

Пример: в форме регистрации подписи, расположенные близко к текстовым полям, подсказывают, что именно нужно ввести. Логотип WWF — панда, сложенная из близко расположенных чёрных пятен на белом фоне.

### UI-дизайн приложения

UI — этап разработки пользовательского интерфейса, на котором создаются все элементы: кнопки, меню, визуальный дизайн. UI и UX должны идти рука об руку [3](https://www.ddplanet.ru/baza-znaniy/uiux-mobile/).

Принципы UI-дизайна:

- Пользователь должен легко ориентироваться в интерфейсе.
- Используйте лаконичные элементы, размещайте компоненты в легкодоступных местах.
- Иконки и иллюстрации должны быть понятными и не перегруженными.
- Текст должен быть легко читаемым и разборчивым.
- Используйте гайдлайны платформ: Material Design для Android, Human Interface Guidelines для iOS.
- Тестируйте приложение на экранах разных размеров.

## Часть 4. UX-процесс: от исследования до релиза и развития продукта

### Общая схема процесса

По данным AppCraft и Surf, разработка дизайна мобильного приложения занимает в среднем 7–12 недель и включает следующие этапы [4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/)[5](https://surf.ru/dizajn-dlya-prilozheniya/):

| Этап | Сроки | Зависит от |
|------|-------|------------|
| Исследование | 1–2 недели | Готовности заказчика |
| Информационная архитектура | 1 неделя | Исследования |
| Wireframing | 1–2 недели | Информационной архитектуры |
| UI-дизайн | 2–4 недели | Вайрфреймов |
| Дизайн-система / UI-kit | 1–2 недели | UI-дизайна |
| Прототипирование | 1 неделя | UI-дизайна |
| Передача в разработку | 3–5 дней | Всех предыдущих этапов |
| **Итого** | **7–12 недель** | — |

### Этап 1. Исследование

Погружаемся в цели и задачи бизнеса, изучаем целевую аудиторию и конкурентов [2](https://netology.ru/blog/09-2020-design-prilojeniy).

Исследования делятся на:

- **Количественные** — отвечают на вопросы «сколько?», «как часто?». Опросы, анкеты, телефонные интервью, аналитика.
- **Качественные** — отвечают на вопросы «кто?», «почему?». Глубинные интервью, фокус-группы, экспертные оценки.

Если приложение делается с нуля: сначала качественные, потом количественные. Если приложение уже есть и его дорабатывают: сначала количественные (статистика), потом качественные.

Далее проводят конкурентный анализ и изучают другие каналы коммуникации бренда: сайт, презентации, рекламу, офлайн-точки. Это нужно для правильного позиционирования и переноса языка бренда в приложение.

Аналитик упаковывает данные в артефакты: mindmap, схемы бизнес-процессов, типичные пользовательские пути. На их основе дизайнер принимает решения. Важно фиксировать требования, чтобы избежать бесконечных доработок.

### Этап 2. Анализ аудитории и сценариев

#### 5W: пять вопросов для определения ЦА

По DD Planet [3](https://www.ddplanet.ru/baza-znaniy/uiux-mobile/):

- **What?** — товар или услуга, которую вы предлагаете.
- **Who?** — тип потребителя: пол, возраст, место жительства, социальный статус.
- **Why?** — какую проблему решает продукт и почему пользователя это заинтересует.
- **When?** — время использования: сезон, праздники, время суток.
- **Where?** — место покупки или использования: офлайн, приложение, сайт.

После 5W выделяют сегменты аудитории и переходят к персонам.

#### Метод персон

Разработан Аланом Купером. Позволяет сосредоточиться на конкретном пользователе, а не на безликой массе. У персоны есть [3](https://www.ddplanet.ru/baza-znaniy/uiux-mobile/):

- **Драйв или мотив** — чего она хочет.
- **Источник драйва** — почему она этого хочет.
- **Контекст использования** — как персона хочет осуществить свои желания.
- **Контекст персоны** — имя, бэкграунд, фото, страхи, мечты, раздражители.

Эмпатия — ключевой навык. Сложно испытывать эмпатию к безликой массе, но персона заставляет думать о пользователе как о знакомом человеке.

Пример персоны:

> **Анна, 28 лет, менеджер проекта.** Использует Android-смартфон среднего сегмента. Открывает приложение в метро по дороге на работе. Хочет за 2–3 минуты проверить статус задач и быстро отметить выполненные. Раздражает, когда нужно много тапов и долгая загрузка.

#### User Journey

По Infogra [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui), User Journey — это ветвистое древо возможностей с разным функционалом: подписка, обращение в поддержку, чтение, оплата. Каждая «ветвь» должна быть хорошо продумана уже на этапе прототипа и вести к целевому действию.

### Этап 3. Проектирование: вайрфреймы и прототипы

По сути это создание скелета приложения: дизайнер понимает, где какая информация, раскидывает контент по экранам и определяет, сколько экранов будет в каждом сценарии [2](https://netology.ru/blog/09-2020-design-prilojeniy).

Инструменты:

- **Бумажные прототипы** — от руки делают эскизы экранов на бумаге. Подходят для быстрого обсуждения идей и синхронизации с командой.
- **Чёрно-белые вайрфреймы** в Figma — проверяют логику и структуру.

Рекомендации по бумажным прототипам [2](https://netology.ru/blog/09-2020-design-prilojeniy):

- Используйте обычную бумагу, а не разлинованную — линии отвлекают.
- Простой карандаш с ластиком позволяет быстро поправлять ошибки.
- Фокус на логике, а не на цвете или стиле.
- Бумага и карандаш — такие же инструменты дизайнера, как графический редактор.

На этапе проектирования не уходите в визуальный дизайн. Не обсуждайте цвет кнопки или радиус скругления. Главное — логика взаимодействия и расположение компонентов.

### Этап 4. Дизайн-концепция

Дизайн-концепция — совокупность дизайнерских решений, дающая общее представление о продукте. На этом этапе [2](https://netology.ru/blog/09-2020-design-prilojeniy):

- подбирают визуальные референсы;
- сверяются с брендбуком;
- прорабатывают один целевой сценарий из 5–6 экранов;
- согласовывают концепцию с клиентом.

Важно презентовать концепцию и показать путь от анализа до решения. «Дизайн говорит сам за себя» — ошибочное мнение. Заказчику нужно объяснить логику, чтобы выровнять ожидания и снять лишние вопросы.

### Этап 5. Визуальный дизайн и UI-kit

После согласования концепции дизайнер дорабатывает приложение [2](https://netology.ru/blog/09-2020-design-prilojeniy):

- покрывает все пользовательские сценарии;
- отрабатывает пограничные состояния: нет интернета, ошибки ввода, успешная/неудачная отправка, пустые экраны, контекстные подсказки;
- приводит дизайн к единому Style Guide.

UI-kit (User Interface Kit) — документ со шрифтами, цветами, формами, размерами иконок, кнопок, шрифтов и количеством текстовых стилей [4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/).

Зачем нужен UI-kit [2](https://netology.ru/blog/09-2020-design-prilojeniy):

- **Упрощает разработку** — разработчик один раз запрограммировал кнопку и копирует её на разные экраны.
- **Формирует привычку к интерфейсу** — если пользователь дважды нажал на синюю кнопку и оба раза произошло одно и то же, формируется связь «действие — последствие».

Если у компании есть дизайн-система, этап вайрфреймов часто сокращается или пропускается — интерфейс собирается из готовых компонентов, как из кубиков Лего.

### Этап 6. Прототипирование и тестирование

Прежде чем отдать макет в разработку, его нужно протестировать. Дизайнер собирает интерактивный прототип в Figma или других сервисах (InVision, Marvel, ProtoPie, Flinto, Principle) [2](https://netology.ru/blog/09-2020-design-prilojeniy).

Разработка — самая дорогая часть продукта. Поэтому важно при помощи прототипа проверить недочёты и исправить ошибки до программирования.

Параметры тестирования [3](https://www.ddplanet.ru/baza-znaniy/uiux-mobile/)[4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/):

- **Эффективность** — достигает ли пользователь своих целей.
- **Результативность** — сколько времени требуется на достижение цели.
- **Удовлетворение** — качество сервиса и пользовательский опыт.

Тестирование проводится на протяжении всей разработки и после релиза. Постоянная проверка на экранах с разным разрешением позволяет найти и исправить ошибки до попадания в сторы. После небольшого обновления или добавления функций что-то может «поехать» на существующих экранах [3](https://www.ddplanet.ru/baza-znaniy/uiux-mobile/).

### Этап 7. Создание спецификации для разработчика

Дизайнер собирает UI-kit и передаёт макеты в разработку. Часто используют Zeplin, где разработчик может посмотреть отступы и размеры элементов [2](https://netology.ru/blog/09-2020-design-prilojeniy).

### Этап 8. Авторский надзор и публикация

После переноса макетов в код дизайнер проверяет соответствие дизайна задаче. При необходимости создаёт задачи на доработку.

Для публикации в сторах дизайнер оформляет страницу приложения и готовит скриншоты для промо-раздела. Текстовое описание готовит менеджер продукта, аналитик или маркетолог [2](https://netology.ru/blog/09-2020-design-prilojeniy).

### Этап 9. После релиза: развитие продукта

Когда аудитория начинает пользоваться приложением, появляются данные: в какие разделы заходят, где не проходят дальше, сколько не завершает покупку. Данные анализируют и дорабатывают приложение. Процесс запускается сначала [2](https://netology.ru/blog/09-2020-design-prilojeniy).

## Часть 5. Исследования: детальная практика

### Когда и какие исследования проводить

По AppCraft [4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/):

**Изучение целей и задач бизнеса**

UX/UI-дизайнер должен мыслить категориями бизнеса — каждый элемент интерфейса служит для достижения цели компании и маркетинговых показателей. Например, во время выхода нового приложения удобный дизайн привлекает и удерживает пользователей. После запуска изменения в интерфейсе могут увеличить конверсию и повысить лояльность.

**Исследование целевой аудитории**

Методы:

- **Интервью с аудиторией** — опросники в Google-таблицах или разговоры по телефону/скайпу.
- **Включённое наблюдение фокус-группы** — изучаем, как пользователи работают и ориентируются, задавая вопросы в процессе.
- **Персоны и сценарии** — выявляем типичных пользователей и их пути.
- **Обращения в техподдержку** — на что жалуются, чего не хватает, какие трудности возникают. Подходит для доработки после запуска.
- **A/B-тестирование** — точечные изменения для проверки гипотез о поведении пользователей.

**Анализ конкурентов**

У каждого бренда есть позиционирование и визуальный язык. Исследование конкурентов помогает найти слабые места, выделить незанятую нишу и не допустить типичных ошибок [4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/).

### Распределение ролей в исследованиях

В зависимости от компании исследования могут делать [2](https://netology.ru/blog/09-2020-design-prilojeniy):

- **Бизнес-аналитик** — погружается в бизнес-процессы, собирает требования компании.
- **UX-аналитик** — изучает проблемы пользователей, проводит качественные и количественные исследования.
- **Продуктовый аналитик** — работает с метриками и показателями продукта.
- **Дизайнер или менеджер продукта** — может совмещать функции, если нет выделенных аналитиков.

## Часть 6. Практические советы по UI для мобильных приложений

### Расположение элементов и навигация

По Infogra и AppCraft [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui)[4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/):

- **Основные элементы управления** размещайте в нижней части экрана — до них легче дотянуться большим пальцем.
- **Верхний левый угол** оставьте для «Назад» или второстепенных действий, потому что до него сложно тянуться.
- **Логотип** не дублируйте на каждом экране: достаточно иконки приложения и экрана загрузки.
- **Нижняя навигация** — 3–5 основных разделов, часто используемые всегда на виду.
- Управление необязательно выполняется только кнопками. Пользователь может смахивать или удерживать элементы.
- Приложения можно скроллить снизу вверх и справа налево. Если используете боковой скролл — дайте подсказку.

### Зоны досягаемости

Ключевые функции должны попадать в зону досягаемости большого пальца. Это особенно важно, когда пользователь держит телефон одной рукой [4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/).

### Типографика и размеры

| Элемент | Размер шрифта | Особенности |
|---------|---------------|-------------|
| Заголовки экранов | 18–24 px | Жирный или полужирный |
| Основной текст | 14–16 px | Основной цвет, хорошая читаемость |
| Подсказки, второстепенный текст | 12–14 px | Светло-серый или secondary color |

Ограничения [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui):

- Не более 5–6 текстовых стилей одного шрифта (разного размера, цвета и толщины).
- Не более 4–5 основных цветов.
- Используйте дифференциацию толщины шрифтов для визуальных акцентов.
- Используйте Material 3 типографику (Display, Headline, Title, Body, Label) для совместимости с Android.
- Не используйте размер шрифта ниже 11 pt на мобильных устройствах [6](https://media.contented.ru/opyt/instrukcii/dizain-mobilnyh-prilozhenii/).

### Цвет и интерактивность

- Цветом показывайте кликабельность и важность: первичное действие, вторичное, опасное, отключенное.
- Цвета должны быть диверсифицированы и нативно подсказывать, какие элементы кликабельны, а какие — нет [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui).
- Для Android тестируйте цвета на дешёвых экранах — избегайте «грязных» и близких по тону цветов. На плохой матрице страдает цветопередача [2](https://netology.ru/blog/09-2020-design-prilojeniy).
- Проверяйте контраст по WCAG: минимум 4.5:1 для текста.

### Подсказки и тултипы

Подсказки — это хорошо. Если есть вероятность, что пользователь несколько раз будет нажимать на некликабельный элемент или у вас есть нестандартные элементы управления — добавьте tooltip [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui).

### Анимация переходов

Стоит продумать анимацию перехода с одного экрана на другой: исчезновение, смещение, прелоадер и другие. Лёгкие анимации при нажатии кнопок дают обратную связь и подтверждение действия. Прогрессивные индикаторы помогают пользователям понять, что происходит и сколько времени это займёт [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui)[4](https://appcraft.pro/blog/razrabotka-uxui-dizajna-mobilnogo-prilozheniya/).

### Адаптивность под разные устройства

- Тестируйте дизайн на 4–5 популярных разрешениях среди вашей аудитории [1](https://infogra.ru/ui/dizajn-mobilnyh-prilozhenij-polnyj-gajd-po-ux-ui).
- Проверяйте, чтобы на разных экранах не пропадали кнопки, не обрезались элементы, шрифт не становился слишком мелким.
- Для Android отладка интерфейса сложнее, чем для iOS, из-за большого количества устройств от разных производителей [2](https://netology.ru/blog/09-2020-design-prilojeniy).
- Учитывайте планшеты, foldable-устройства и ChromeOS — современный Android выходит за рамки телефонов.
- Проверяйте адаптивность с помощью constraints в Figma: элементы должны растягиваться и правильно масштабироваться [6](https://media.contented.ru/opyt/instrukcii/dizain-mobilnyh-prilozhenii/).

### Размеры интерактивных элементов

- Material Design для Android: интерактивные элементы не менее 48 × 48 dp, между ними минимум 8 dp [7](https://www.uprock.ru/education/razmery-ui-elementov-v-prilozheniyah).
- Apple HIG: минимум 44 × 44 px для тач-элемента.
- По Стивену Хуберу: в верхней части экрана 11 мм (31 pt / 42 px), в нижней — 12 мм (34 pt / 46 px), в центре можно меньше — 7 мм (20 pt / 27 px) [7](https://www.uprock.ru/education/razmery-ui-elementov-v-prilozheniyah).

## Часть 7. UI-kit в Figma на основе Material Design 3 для Android

Это практическое дополнение к обзорным разделам. Здесь пошагово собран процесс создания UI-kit в Figma, который можно передать разработчикам для реализации на Jetpack Compose.

### 7.1. Подготовка файла Figma

1. Создайте новый файл **Mobile App UI-kit**.
2. Подключите официальный Figma-кит **Material 3 Design Kit** (Community → Material Design 3).
3. Настройте страницы файла:
   - `🎯 Cover` — обложка проекта.
   - `📝 Documentation` — правила использования UI-kit.
   - `🎨 Color & Typography` — цвета и шрифты.
   - `🧩 Components` — библиотека компонентов.
   - `📱 Screens` — макеты экранов.
   - `🧪 Prototype` — кликабельный прототип.

### 7.2. Настройка цветовой системы (Color Tokens)

Material 3 строится на токенах цвета. В Figma создайте переменные (`Local variables`):

| Токен | Назначение | Пример светлой темы |
|-------|------------|---------------------|
| `primary` | Основной акцент | `#6750A4` |
| `onPrimary` | Текст/иконки на primary | `#FFFFFF` |
| `primaryContainer` | Фон для акцентных элементов | `#EADDFF` |
| `onPrimaryContainer` | Текст на primaryContainer | `#21005D` |
| `secondary` | Вторичный акцент | `#625B71` |
| `surface` | Фон карточек/экранов | `#FEF7FF` |
| `onSurface` | Основной текст | `#1D1B20` |
| `outline` | Границы и разделители | `#79747E` |
| `error` | Ошибка/опасное действие | `#B3261E` |

Создайте две коллекции переменных: `Light` и `Dark`. Это позволит быстро переключать темы.

### 7.3. Настройка типографики

Material 3 использует 5 групп стилей:

| Группа | Назначение | Размеры (пример) |
|--------|------------|------------------|
| Display | Крупные заголовки, брендинг | 36–57 px |
| Headline | Заголовки экранов | 28–32 px |
| Title | Заголовки карточек/разделов | 16–22 px |
| Body | Основной текст | 14–16 px |
| Label | Кнопки, подписи, теги | 11–14 px |

В Figma создайте текстовые стили с именами:

- `Display/Large`
- `Headline/Medium`
- `Title/Small`
- `Body/Medium`
- `Label/Large`

Для каждого стиля задайте шрифт (например, Roboto или Google Sans), размер, вес и межстрочный интервал.

### 7.4. Базовые компоненты UI-kit

#### Кнопки

- `Button/Primary` — основное действие, залитый цветом `primary`.
- `Button/Secondary` — вторичное действие, обводка или менее акцентный фон.
- `Button/Text` — третичное действие, только текст.
- `Button/FAB` — плавающая кнопка действия.
- `Button/Icon` — кнопка с иконкой.

Для каждой кнопки создайте состояния: `Default`, `Hovered`, `Pressed`, `Disabled`, `Focused`.

#### Поля ввода

- `TextField/Outlined` — с обводкой.
- `TextField/Filled` — с заливкой фона.
- Состояния: `Default`, `Focused`, `Error`, `Disabled`.
- Добавьте текстовые стили для label, placeholder, введённого текста и supporting text.

#### Карточки и списки

- `Card/Elevated` — с тенью.
- `Card/Filled` — с заливкой.
- `Card/Outlined` — с обводкой.
- `ListItem` — элемент списка с иконкой, текстом и дополнительным действием.

#### Навигация

- `TopAppBar` — верхняя панель с заголовком и иконками.
- `BottomNavigation` — нижняя навигация с 3–5 пунктами.
- `NavigationDrawer` — боковое меню для планшетов.
- `Tabs` — вкладки для переключения контента.

#### Диалоги и уведомления

- `Dialog/Alert` — диалог с подтверждением.
- `Snackbar` — короткое сообщение внизу экрана.
- `Toast` — лёгкое уведомление (в Compose заменяется на Snackbar).
- `ProgressIndicator` — круговой и линейный индикаторы загрузки.

### 7.5. Состояния и крайние случаи

Для каждого экрана и компонента продумайте состояния:

| Состояние | Описание | Пример решения |
|-----------|----------|----------------|
| **Default** | Нормальное состояние | Стандартный вид компонента |
| **Loading** | Загрузка данных | Скелетон или индикатор |
| **Empty** | Нет данных | Иллюстрация + поясняющий текст + CTA |
| **Error** | Ошибка загрузки | Сообщение + кнопка «Повторить» |
| **Offline** | Нет интернета | Баннер и кэшированные данные |
| **Success** | Успешное действие | Snackbar или анимация |

### 7.6. Адаптивность и автолейаут

- Используйте **Auto Layout** для всех компонентов.
- Задайте фиксированные ширины макетов под типичные разрешения: 360 dp, 393 dp, 412 dp, 768 dp (планшет), 1024 dp (foldable).
- Создайте компоненты с `constraints`, чтобы они растягивались корректно.
- Проверяйте, как UI выглядит при увеличении шрифта (accessibility — размер шрифта 200%).

### 7.7. Передача в разработку

Перед передачей разработчикам убедитесь, что [8](https://infogra.ru/articles/articles-design/sozdanie-ui-ux-dizajna-mobilnogo-prilozheniya-polnyj-gajd-s-nulya-do-revju-interfejsa):

- все цвета оформлены как переменные;
- типографика оформлена как стили;
- все компоненты имеют понятные имена и состояния;
- экраны разложены по флоу;
- интерактивный прототип собран и проверен;
- описаны крайние состояния и анимации;
- есть подробные спецификации: размеры, отступы, цвета, шрифты;
- есть примеры состояний: не только стандартные экраны, но и loading, error, empty;
- есть отдельная страница с документацией.

## Часть 8. Архитектура Android-приложений

### Общие принципы

Хорошая архитектура делает приложение:

- масштабируемым;
- поддерживаемым;
- устойчивым к расширению экосистемы устройств (телефоны, планшеты, foldable, ChromeOS, Wear OS, TV).

Основной принцип — **разделение ответственности** (separation of concerns). Каждый слой и класс имеют чёткую роль и минимальную связность.

> Не храните данные и состояние в компонентах приложения (`Activity`, `Service`, `BroadcastReceiver`), так как система может уничтожить их в любой момент.

### Слои приложения

```
┌─────────────────────────────────────┐
│           UI-слой                   │
│  Jetpack Compose + ViewModel        │
├─────────────────────────────────────┤
│        Domain-слой (опционально)    │
│  Use Cases / Interactors             │
├─────────────────────────────────────┤
│           Data-слой                 │
│  Repositories + Data Sources         │
│  (сеть, база, файлы, кэш)            │
└─────────────────────────────────────┘
```

#### UI-слой

- Отображает данные на экране.
- Реагирует на изменения состояния.
- `ViewModel` — держатель состояния, живёт при смене конфигурации.
- `Jetpack Compose` — декларативный UI.

#### Domain-слой (опционально)

- Инкапсулирует сложные или переиспользуемые сценарии.
- Use Cases / Interactors используются несколькими ViewModel.
- Полезен, когда логика становится объёмной и переиспользуемой.

#### Data-слой

- Содержит бизнес-логику работы с данными.
- `Repository` — единый источник данных для UI.
- `Data Source` — конкретные источники: сеть (Retrofit), база (Room), файлы, кэш.

### Ключевые паттерны

#### Single Source of Truth (SSOT)

Для каждого типа данных определите единственный источник истины — сущность, которая владеет данными и может их изменять. SSOT:

- выдаёт данные в неизменяемом виде;
- изменяет данные только через явные методы или события.

Пример: `NoteRepository` — единственный источник заметок. Все ViewModel получают заметки через него.

#### Unidirectional Data Flow (UDF)

```
Источники данных → UI → События пользователя → Источники данных
```

- Состояние течёт сверху вниз: из источников к UI.
- События идут снизу вверх: из UI к источникам.
- Это делает поток данных предсказуемым и упрощает отладку.

### Best practices по архитектуре

- Минимизируйте зависимость от Android-классов: большинство классов должны быть платформенно-агностичными и легко тестируемыми.
- Чётко определяйте границы модулей.
- Не смешивайте в одном классе несвязанные обязанности (например, кэширование и привязку к UI).
- Проектируйте переиспользуемые и композиционные UI-компоненты.
- Сохраняйте состояние UI при конфигурационных изменениях (поворот, смена размера окна, foldable).

## Часть 9. Jetpack Compose: best practices UI и производительности

### Минимизация вычислений в Composable-функциях

Composable-функции могут вызываться очень часто (например, каждый кадр анимации). Поэтому внутри них нужно выполнять минимум тяжёлых вычислений.

Для кеширования используйте `remember`:

```kotlin
val formattedDate = remember(date) {
    date.format("dd MMMM yyyy")
}
```

### Lazy-layout и стабильные ключи

При работе с `LazyColumn`/`LazyRow` передавайте стабильные ключи:

```kotlin
LazyColumn {
    items(items = notes, key = { it.id }) { note ->
        NoteItem(note)
    }
}
```

Это позволяет Compose не пересоздавать весь список при перемещении одного элемента.

### derivedStateOf и ограничение рекомпозиций

Быстро меняющееся состояние (например, позиция скролла) может вызывать частые рекомпозиции. Используйте `derivedStateOf`:

```kotlin
val firstVisibleItem by remember {
    derivedStateOf { listState.firstVisibleItemIndex }
}
```

Производное состояние обновляется только при значимых изменениях.

### Отложенные чтения состояния

Чтение состояния сдвигайте в более поздние фазы (layout или draw), используя модификаторы с лямбдами:

```kotlin
Box(
    modifier = Modifier.offset {
        IntOffset(x = offsetX.value.toInt(), y = 0)
    }
)
```

Это позволяет пропускать фазу композиции и обновлять только размещение/отрисовку.

### Избегание обратных записей

Compose предполагает, что вы не пишете в состояние после того, как его прочитали в той же композиции. Нарушение может привести к бесконечным рекомпозициям.

Запись в состояние должна происходить только в ответ на события (`onClick`, `onChange`), а не как побочный эффект чтения в UI-коде.

### Чек-лист производительности Compose

- [ ] Тяжёлые вычисления вынесены в `remember`/`derivedStateOf`.
- [ ] В `LazyColumn`/`LazyRow` используются стабильные ключи.
- [ ] Быстро меняющееся состояние читается через `derivedStateOf`.
- [ ] Используются модификаторы с лямбдами для отложенного чтения.
- [ ] Нет записи в состояние во время композиции.
- [ ] Composable-функции стабильны и не принимают лишние параметры.
- [ ] Профилирование проведено с помощью Layout Inspector и Macrobenchmark.

## Часть 10. Частые ошибки начинающих и как их избежать

### UX

| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Копирование веб-интерфейса | Неудобно на телефоне | Проектировать под мобильный контекст |
| Игнорирование исследований | Решения не отвечают на реальные боли | Проводить интервью и тестирование |
| Слишком много функций на старте | Перегрузка интерфейса | Фокус на MVP и главном сценарии |
| Пропуск состояний ошибок | Пользователь не понимает, что произошло | Продумать loading, error, empty, offline |
| Длинные формы без дробления | Пользователь бросает заполнение | Дробить на шаги или упрощать ввод |
| Не учитывать различия Android/iOS | Пользователям непривычно | Следовать гайдлайнам платформы |

### UI

| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Мелкие элементы | Промахи по кнопкам | Минимум 48 × 48 dp для зоны нажатия |
| Слишком много цветов | Хаос и отсутствие стиля | 4–5 основных цветов + Material 3 токены |
| Несогласованная типографика | Непрофессиональный вид | Использовать систему текстовых стилей |
| Игнорирование тёмной темы | Неудобно в ночном режиме | Создавать переменные для Light/Dark |
| Дублирование логотипа на каждом экране | Захламлённый интерфейс | Достаточно иконки и splash screen |
| Сложные цвета на Android | Плохая цветопередача на дешёвых экранах | Избегать грязных и смежных цветов |

### Архитектура и код

| Ошибка | Последствие | Решение |
|--------|-------------|---------|
| Логика в Activity/Fragment | Сложно тестировать и поддерживать | Переносить в ViewModel и Repository |
| Данные в UI-классах | Потеря состояния при повороте | Хранить состояние в ViewModel |
| Прямое обращение к сети/БД из UI | Жёсткая связанность | Использовать Repository и SSOT |
| Пропуск производительности Compose | Подтормаживания | remember, stable keys, derivedStateOf |

## Заключение

Хороший Android-продукт рождается на стыке трёх компетенций:

1. **Понимание пользователя** — исследования, сценарии, тестирование, метрики после релиза.
2. **Системный визуальный дизайн** — UI-kit в Figma на базе Material 3.
3. **Чистая архитектура** — Jetpack Compose, ViewModel, Repository, UDF, SSOT.

Используйте этот документ как опорный план: начните с персоны и сценария, соберите UI-kit в Figma, а затем реализуйте его в коде с соблюдением архитектурных принципов. Помните: дизайнер делает приложение для других, а не для себя — пользователям нужно решение их задач, а не бесполезный для них креатив.
